# ADR 0002. Публикация сайта: Caddy в контейнере

Дата: 2026-09-25. Состояние: принято.

## Контекст

Человек просит «подготовить всё, чтобы опубликовать на сервере и запустить
сайт». Сервера данных ещё нет (`docs/plans/phase-01-server.md`): сайт –
набор статических файлов, данные – в браузере пользователя. Публиковать
нужно именно это, не выдавая за готовую систему.

Требования:

- **HTTPS обязателен.** Пароли проверяются через WebCrypto
  (`store/password.ts`), а браузер даёт его только в защищённом контексте:
  по `http://IP` вход не работает вовсе.
- **Адреса страниц сайта** (`/documents/…`, `/admin`) отдают `index.html`.
- **Код сайта не должен скачиваться кем угодно**: в нём реквизиты компаний.
- **Заголовки безопасности**, которые нельзя задать в `<meta>`:
  `frame-ancestors`, HSTS, `X-Content-Type-Options`.
- Обслуживать должен человек без опыта администрирования: минимум шагов,
  сертификат продлевается сам.

## Решение

Один контейнер: Caddy 2.8 с собранным сайтом (`deploy/Dockerfile`,
`deploy/Caddyfile`, `deploy/docker-compose.yml`).

- Caddy сам получает и продлевает сертификат Let's Encrypt – без certbot и
  cron.
- Пароль на весь сайт (`basic_auth`) по умолчанию: код с реквизитами не
  отдаётся без него.
- Сборка сайта – в контейнере (`node:22-bookworm-slim`, `npm ci` по
  `package-lock.json`); тесты – до упаковки, у разработчика
  (`scripts/deploy/pack.ps1`).
- Пакет для сервера – `git archive` закоммиченного состояния: без
  `node_modules`, `.env` и незакоммиченных правок.

## Альтернативы

- **nginx + certbot.** Больше движущихся частей: отдельный выпуск и
  продление сертификата, cron, перезагрузка nginx. Для одного статического
  сайта выгоды нет.
- **Статический хостинг (Netlify, Cloudflare Pages, GitHub Pages).** Проще
  всего, но код с реквизитами компаний уходит к стороннему сервису за
  рубежом, а пароль на весь сайт там платный или недоступен. Когда
  появится сервер данных, всё равно нужен свой сервер.
- **Отдавать `dist` через Go-сервер `backend/cmd/api`.** Появится смысл,
  когда у сервера будет API; сейчас это HTTPS и заголовки руками в Go.

## Последствия

- Новые зависимости только для публикации: образы `node:22-bookworm-slim` и
  `caddy:2.8-alpine`. В код сайта ничего не добавлено.
- Проверено без Docker (на машине разработчика он не запускается): Caddy
  2.8.4 с этим `Caddyfile` на собранном сайте – пароль сайта (401 без него),
  заголовки, адреса страниц, кеш и сжатие; полный сценарий в Chrome через
  Caddy, включая «Скачать PDF» и выгрузку в Excel, – без ошибок. Сама
  сборка образа (`docker compose build`) на этой машине не проверена.
- Когда появится сервер данных, Caddy останется перед ним: `/api/*` уйдёт
  на Go-сервер (`reverse_proxy`), остальное – как сейчас.
