# Блокирует этап 0

## Q1. Среда разработки

Проверено 2026-09-21 на этой машине: `go1.27.0 windows/386`; `docker info` не находит демон; `wsl` сообщает, что подсистема Windows для Linux не установлена; `make` отсутствует; `pnpm` отсутствует (есть npm 11.12.1); проект лежит в OneDrive, в пути есть пробел.

Без Docker не работает ни `make dev`, ни `make check` — интеграционные тесты идут на настоящем PostgreSQL через testcontainers.

Предлагаю:

1. Установить WSL2 и запустить Docker Desktop на WSL2-бэкенде.
2. Переустановить Go как **windows/amd64** (или вести разработку внутри WSL2 — тогда Go ставится в Linux). 32-битная сборка упирается в память на линтерах и тестах.
3. Перенести проект из OneDrive в путь без пробелов, например `C:\dev\docflow`. OneDrive синхронизирует `.git` и `node_modules`: это блокировки файлов, порча индекса git и лишний трафик.
4. Вместо GNU make взять `go-task` (`Taskfile.yml`): один бинарник, одинаково работает в Windows, WSL и CI. Цели те же — `task dev`, `task check`. Альтернатива — работать только внутри WSL2 и оставить `Makefile`.
5. Зафиксировать `pnpm` или `npm`.

**Вопрос:** согласны на 1–3? Что выбираем в 4 (`task` / `make` внутри WSL2) и 5 (`pnpm` / `npm`)?

## Q6. Один человек — один аккаунт на все 4 компании?

В архитектуре: «один человек может быть юристом в компании А и работником в компании Б». Значит `users` — общая таблица вне изоляции компаний. Следствия: логин уникален на всю группу; админ компании А при создании пользователя может по сообщению об ошибке узнать, что такой логин уже есть в компании Б.

**Вопрос:** подтверждаете единый аккаунт на группу? Если да, принимаю правило: админ компании не видит и не может найти пользователей без роли в его компании, а при совпадении логина получает нейтральное «создать не удалось, обратитесь к администратору платформы».

## Q7. Документ в нескольких разделах: чей он

Право записывается как `раздел.профиль.действие`, при этом один тип документа может показываться в нескольких разделах (NDA, доверенность, договор о полной материальной ответственности). Если проверять право по любому разделу показа, специалист по закупкам получит доступ к кадровому документу.

Предлагаю: у каждого типа документа ровно один **владеющий раздел** (`owner_section`) — по нему проверяется право; остальные (`display_sections`) влияют только на то, где документ виден в меню, и доступа не дают.

**Вопрос:** принимаем? Если да, для документов-дублей на этапе 8 надо будет указать владеющий раздел.

## Q8. `sensitive` — это право или уровень допуска

В архитектуре одновременно: профиль `sensitive` с правом `раздел.sensitive.view` и отдельное условие «конфиденциальность ≤ допуск». При этом поля «допуск» нет ни у пользователя, ни в ролях, а уровни конфиденциальности нигде не перечислены.

Предлагаю оставить **только право по профилю** (`hr.sensitive.view`), а `confidentiality` ввести как ортогональный уровень с фиксированной шкалой: 0 — открытый, 1 — внутренний, 2 — конфиденциальный, 3 — коммерческая тайна; допуск хранится у пользователя в рамках компании.

**Вопрос:** нужны ли оба механизма или достаточно прав по профилю? Если оба — подходит ли шкала из 4 уровней?

## Q9. Кто утверждает документы о директоре и кто такой участник

Раздел 3 списка (корпоративное управление) — это решения участников и совета директоров: «Решение единственного участника», «Протокол общего собрания», «Решение о назначении директора».
